# 性能の確認（本番の約5倍のテストデータ）

要件定義書 7章「規模と性能」の「集計はインデックスを前提に設計し、テストデータで速度を確かめる」の記録です。一覧・詳細・集計・CSV を本番の約5倍のデータで測り、1秒を超えるもの・データが増えると遅くなるものを直しました。

## 方法

- データ：`bun run db:seed -- --scale=full --today=2026-11-02`（`src/infra/seed`）。件数は下の表
- 環境：手元の `wrangler dev --local`（workerd と Durable Object の SQLite）。開発用の仮想マシン（2 vCPU）で、ほかの作業と同居していたため、時間は目安（測ったときの負荷は load average 2〜3。同じ画面でも回によって ±30% ほどぶれる）。本番の Workers とは CPU が異なる
- 測り方：`bun run perf -- --url=http://localhost:8798 --today=2026-11-02`（`scripts/perf.mjs`）。開発用ログイン（管理者）で、各画面を1回読み込んでから5回要求し、応答の本文を受け取るまでの時間の中央値。手元なので通信の時間はほぼなく、Worker（画面の組み立て）と業務 DB（照会）の時間
- 変更前と変更後は同じデータで比べた。変更前は変更の直前のコード（`0926bdc`）で、データの写しから下の索引を消したもの。変更後はすべての変更を入れたコード（`18b5dad`）
- SQL だけの時間とクエリプランは、Durable Object の SQLite のファイルを Python の sqlite3 で開いて確かめた（`EXPLAIN QUERY PLAN`）
- 目標：通常の操作は1秒以内に画面が更新される（要件定義書 1章・7章）。件数の多い CSV・一括 PDF は非同期

## 変更したこと

### 索引（マイグレーション `0005_performance_indexes`）

| 索引                                                                                                        | 使うところ                                                                                       |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `sales_orders (ship_planned_on, number)`                                                                    | 受注一覧の並び。並べ替えずに1ページ分だけ読み、明細の件数などの副問い合わせも1ページ分だけになる |
| `purchase_orders (ordered_on, number)`                                                                      | 発注一覧の並びと発注日の絞り込み                                                                 |
| `invoices (issued_on, number)`                                                                              | 請求書一覧の並びと発行日の絞り込み                                                               |
| `receipts (received_on)`                                                                                    | 集計（仕入）。入荷の明細をすべて読まない                                                         |
| `shipments (invoice_id, shipped_on)`                                                                        | 未請求の発送を期間で探す（発送ごとの請求書の見積もりと発行、締め処理）                           |
| `sales_orders (split_from_id)`                                                                              | 受注の取得のたびに分割先の受注を探す（受注詳細・発送・一括発送）。SQL で 1回 17ms → 1ms          |
| `customer_payments (customer_id, cancelled, amount)`、`payment_allocations (payment_id, cancelled, amount)` | 売掛残高の入金と消込の集計を、表を読まずに索引だけで足す                                         |
| `documents (status)`                                                                                        | ダッシュボードの「PDF の作成に失敗した帳票」の件数                                               |

### 照会の書き方（区分の外のストアも含む）

- 締め処理（billing）：締め日のある販売先の最も古い未請求の発送の日を、販売先ごとの副問い合わせ（販売先の数 × 未請求の発送を読む）ではなく、未請求の発送の1回の集計で求める。締め処理の対象の一覧は、期間をすべて含む範囲の未請求の発送を1回で読んで販売先ごとに分ける（`InvoiceStore.closingCustomers`、`closingCandidates`）
- 売掛残高（billing）：販売先ごとの9つの副問い合わせ（期限超過の分は販売先に関係なく期限超過の請求書をすべて読んでいた）をやめ、未入金・一部入金の請求書、入金、消込をそれぞれ1回ずつ集計して結びつける。販売先の数だけの行なので、すべて読んでからページに分ける（`CustomerPaymentStore.receivables`）
- 送付に失敗した帳票・請求書の件数（platform・billing）：帳票・請求書ごとに最新の送付を調べず、結果が「失敗」の送付から探す

### テストデータ

- 請求の区分（返品伝票・請求書・締め処理・入金と消込・販売先廃棄）は、取引の後にまとめてではなく、毎日の取引の最後に行う。後からまとめて請求すると、途中までは3年分の発送（約11万件）が未請求のまま残り、上の締め処理の照会が1回1分かかって投入が終わらなかった
- 土曜の発送を月曜に請求する（日曜が休みのため、締め日のない販売先の土曜の発送が未請求のまま残っていた）。整合の確認に「締め日のない販売先の発送は、今日の分を除いて請求済み」を足した

## 残っていること・気づいたこと

- 集計（商品別・36か月）は約1.2秒。3年分の受注明細（約40万行）を月 × 商品（約8万組）に集計する時間で、索引では縮まらない（受注明細を読む索引を足しても 781ms → 751ms）。既定の12か月は 0.4〜0.5秒、本番の量（1/5）なら36か月でも 0.3秒ほどの見込み。速くするなら月ごとの集計表を持つ
- 一覧の深いページ（OFFSET）は、前のページの行を読み飛ばすので、ページが進むほど遅くなる（受注一覧の2000ページ目で 160ms）。ふつうは絞り込みで探す
- 受注一覧のキーワード（0.7秒）は、受注番号・販売先・明細の商品名を LIKE で探すため、受注の数に比例する。量が増えるなら全文検索の索引を考える
- 未請求の発送を探す照会は、未請求の発送の数に比例する。請求が毎日・毎月行われていれば千件ほど（今日の時点で 1,170件）だが、移行などで過去の発送を未請求のまま入れると締め処理の画面が遅くなる。過去の発送は請求済みとして移す
- 売掛残高は、入金と消込のすべての履歴を集計する（いまは 0.2秒）。年数とともに伸びるので、10年分を超えるなら入金ごとに消込済みの額を持つ
- 非同期の CSV（2,000件を超えるもの）が終わるまでの時間は測っていない（ジョブは 200件ずつ OFFSET で読む）

## テストデータの投入の時間

同じ仮想マシンで、ほかの作業（テスト・E2E・ほかの投入）と同居していたときの時間です。

| 規模                          | 実行したユースケース | 時間                                      |
| ----------------------------- | -------------------: | ----------------------------------------- |
| tiny（結合テスト用）          |               千数百 | 数秒（`tests/integration/seed.test.ts`）  |
| small（既定）                 |                7,889 | 約36秒（負荷が高いときは1分ほど）         |
| full（`--scale=full`、3年分） |              476,602 | 約60分（取引先 2秒・商品 9秒・取引 59分） |

full は1回分（7日分）ずつ依頼するので、途中で止まっても `--skip-to=operations:<回>` で続きから再開できます（済んだ回は二重に投入しません）。
