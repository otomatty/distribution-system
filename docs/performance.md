# 性能の確認（本番の約5倍のテストデータ）

要件定義書 7章「規模と性能」の「集計はインデックスを前提に設計し、テストデータで速度を確かめる」の記録です。一覧・詳細・集計・CSV を本番の約5倍のデータで測り、1秒を超えるもの・データが増えると遅くなるものを直しました。

## 方法

- データ：`bun run db:seed -- --scale=full --today=2026-11-02`（`src/infra/seed`）。件数は下の表
- 環境：手元の `wrangler dev --local`（workerd と Durable Object の SQLite）。開発用の仮想マシン（2 vCPU）で、ほかの作業（テスト・E2E）と同居していたため、時間は目安（測ったときの負荷も書く）。本番の Workers とは CPU が異なる
- 測り方：`bun run perf -- --url=http://localhost:8798 --today=2026-11-02`（`scripts/perf.mjs`）。開発用ログイン（管理者）で、各画面を1回読み込んでから5回要求し、応答の本文を受け取るまでの時間の中央値と最大。手元なので通信の時間はほぼなく、Worker（画面の組み立て）と業務 DB（照会）の時間
- 変更前と変更後は同じデータで比べた。変更後は下の変更をすべて入れたコード、変更前は変更の直前のコード（`0926bdc`）で、データの写しから 0005 の索引を消したもの
- SQL だけの時間とクエリプランは、Durable Object の SQLite のファイルを Python の sqlite3 で開いて確かめた（`EXPLAIN QUERY PLAN`）
- 目標：通常の操作は1秒以内に画面が更新される（要件定義書 1章・7章）。件数の多い CSV・一括 PDF は非同期
